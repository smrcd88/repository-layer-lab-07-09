# Guía práctica — Capa de persistencia con Spring Boot 4, Spring Data JPA y PostgreSQL

## 1. Propósito de la guía

El objetivo no es que el estudiante aprenda simplemente a escribir:

```java
public interface StudentRepository extends JpaRepository<Student, Long> {
}
```

sino que comprenda qué ocurre detrás de esta interfaz y sea capaz de responder preguntas como:

- ¿Cómo pasar de un requerimiento de negocio a un modelo relacional?
- ¿Dónde debe estar una clave foránea?
- ¿Qué entidad es propietaria de una relación?
- ¿Cuándo utilizar `@OneToMany`, `@ManyToOne`, `@ManyToMany` o `@OneToOne`?
- ¿Qué operaciones ya proporciona Spring Data?
- ¿Cuándo utilizar `findBy...`?
- ¿Cuándo un Query Method se vuelve demasiado complejo?
- ¿Cuándo utilizar `@Query`?
- ¿Cuál es la diferencia entre JPQL y SQL?
- ¿Qué SQL termina ejecutando Hibernate?
- ¿Cómo evitar el problema N+1?
- ¿Por qué no probar contra H2 si producción utiliza PostgreSQL?
- ¿Cómo validar que las migraciones Flyway realmente funcionan?
- ¿Cómo probar la persistencia contra PostgreSQL real sin instalar una base de datos manualmente?

La meta final es que el estudiante pueda diseñar y defender técnicamente una capa de persistencia.

## Módulo 1. Modelo de datos

### 1.1 Antes de JPA: pensar en datos

Supongamos el requerimiento:

> CourseHub debe registrar estudiantes con nombre, email y fecha de nacimiento.

Antes de crear una clase Java debemos pensar:

```text
STUDENT
--------------------------------
id
name
email
birth_date
```

En PostgreSQL:

```sql
CREATE TABLE student (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(120) NOT NULL,
    email VARCHAR(180) NOT NULL UNIQUE,
    birth_date DATE
);
```

El concepto importante es:

```text
Modelo de dominio != Modelo relacional
```

Aunque muchas veces se parezcan.

---

## Módulo 2. Entidades JPA

Representamos la tabla mediante:

```java
@Entity
@Table(name = "student")
public class Student {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, length = 120)
    private String name;

    @Column(nullable = false, unique = true, length = 180)
    private String email;

    private LocalDate birthDate;

    protected Student() {
    }

    public Student(String name, String email, LocalDate birthDate) {
        this.name = name;
        this.email = email;
        this.birthDate = birthDate;
    }
}
```

Responsabilidad de:

```text
@Entity
@Table
@Id
@GeneratedValue
@Column
```

Pero especialmente diferenciar:

```text
@Entity
```

de:

```text
tabla
```

La entidad pertenece al modelo Java.

La tabla pertenece al modelo relacional.

Hibernate realiza el mapeo entre ambas.

# Módulo 3. Relaciones

## 3.1 Relación 1:N

Requerimiento:

> Un departamento ofrece muchos cursos, pero cada curso pertenece a un único departamento.

Modelo relacional:

```text
department
----------
id PK
name

course
------
id PK
name
department_id FK
```

La FK está en el lado N.

Por lo tanto:

```java
@Entity
public class Course {

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "department_id", nullable = false)
    private Department department;
}
```

Y opcionalmente:

```java
@Entity
public class Department {

    @OneToMany(mappedBy = "department")
    private List<Course> courses = new ArrayList<>();
}
```

Concepto esencial:

```text
Department 1 ------ N Course
                        ↑
                        │
                  contiene FK
```

En una relación bidireccional:

```java
mappedBy = "department"
```

indica que `Course.department` controla la relación.

---

# 3.2 Relación 1:1

Requerimiento:

> Cada estudiante tiene como máximo un perfil académico.

Modelo:

```text
student
-------
id

student_profile
---------------
id
student_id UNIQUE FK
biography
linkedin_url
```

Entidad:

```java
@OneToOne(fetch = FetchType.LAZY, optional = false)
@JoinColumn(
    name = "student_id",
    nullable = false,
    unique = true
)
private Student student;
```

El `UNIQUE` en la FK es lo que realmente garantiza el 1:1 en la base de datos.

Jakarta Persistence especifica precisamente que una asociación `@OneToOne` suele mapearse mediante una FK única o mediante una PK compartida.

---

# 3.3 Relación N:M

Supongamos:

```text
Student
   N
   │
   │
   M
 Course
```

En una base relacional necesitamos:

```text
student_course
--------------
student_id
course_id
```

JPA permite:

```java
@ManyToMany
@JoinTable(
    name = "student_course",
    joinColumns = @JoinColumn(name = "student_id"),
    inverseJoinColumns = @JoinColumn(name = "course_id")
)
private Set<Course> courses = new HashSet<>();
```

Pero debemos introducir desde el comienzo una advertencia.

Si mañana necesitamos guardar:

```text
fecha de matrícula
estado
nota
tipo de matrícula
```

la tabla intermedia ya tiene identidad de negocio.

Entonces debemos crear:

```text
Enrollment
```

y reemplazar:

```text
@ManyToMany
```

por:

```text
Student 1:N Enrollment
Course  1:N Enrollment
```

# Módulo 4. LAZY vs EAGER

Este concepto debe introducirse desde fundamentos.

Por defecto, JPA históricamente establece `EAGER` para asociaciones `@ManyToOne` y `@OneToOne`. La documentación de Jakarta Persistence y Hibernate advierte que cargar asociaciones innecesariamente puede producir problemas y recomienda diseñar explícitamente las estrategias de carga.

Por eso utilizaremos habitualmente:

```java
@ManyToOne(fetch = FetchType.LAZY)
```

en lugar de depender de los defaults.

Regla inicial:

> No cargues información únicamente porque existe una relación.

Si consultamos un estudiante:

```java
studentRepository.findById(1L);
```

no significa necesariamente que necesitemos también:

```text
perfil
matrículas
cursos
departamentos
profesores
```

```text
        ▼
```

# Módulo 6. Métodos heredados

```java
save(entity)
saveAll(entities)

findById(id)
findAll()
findAllById(ids)

existsById(id)

count()

delete(entity)
deleteById(id)
deleteAll()
```

`JpaRepository` agrega operaciones relacionadas con flush como:

```java
flush()
saveAndFlush(entity)
```

Para cada requerimiento decidir si se necesita crear un método nuevo.

### Caso A

> Buscar estudiante por ID.

No crear:

```java
findStudentById(...)
```

Ya existe:

```java
findById(...)
```

### Caso B

> Saber si un estudiante existe.

No hacer:

```java
findById(id).isPresent()
```

si solamente necesitamos conocer existencia.

Preferir:

```java
existsById(id)
```

### Caso C

> Contar estudiantes.

Usar:

```java
count()
```

# Módulo 7. Query Methods

Ahora introducimos consultas derivadas.

```java
Optional<Student> findByEmail(String email);
```

Spring Data analiza:

```text
find
By
Email
```

y genera aproximadamente:

```sql
SELECT ...
FROM student
WHERE email = ?
```

Spring Data permite derivar consultas utilizando propiedades de la entidad y operadores como `And`, `Or`, `Between`, `GreaterThan`, `LessThan`, `Like`, `Containing`, `IgnoreCase`, `OrderBy`, `First` y `Top`.

Ejemplos:

```java
List<Student> findByNameContainingIgnoreCase(String name);
```

```java
List<Student> findByBirthDateAfter(LocalDate date);
```

```java
boolean existsByEmail(String email);
```

```java
long countByActiveTrue();
```

```java
List<Student> findTop10ByOrderByNameAsc();
```

# Módulo 8. ¿Cuándo dejar de usar Query Methods?

Este método es razonable:

```java
findByEmail(String email)
```

Este también:

```java
findByNameContainingIgnoreCase(String name)
```

Pero esto empieza a convertirse en una señal de alerta:

```java
findByNameContainingIgnoreCaseAndActiveTrueAndBirthDateBetweenOrderByNameAsc(
    String name,
    LocalDate from,
    LocalDate to
);
```

Spring Data puede interpretarlo.

El problema no es técnico.

El problema es de:

```text
legibilidad
mantenibilidad
intención
```

Por ello introducimos la primera regla de decisión:

```text
Consulta sencilla
      ↓
Query Method

Consulta compleja
      ↓
@Query / JPQL
```

La propia documentación de Spring Data señala que una consulta derivada deja de ser conveniente cuando el parser no soporta la necesidad o cuando el nombre del método resulta innecesariamente complejo.

# Módulo 9. @Query

Ejemplo:

```java
@Query("""
    select s
    from Student s
    where lower(s.name) like lower(concat('%', :name, '%'))
      and s.active = true
""")
List<Student> searchActiveStudents(String name);
```

Aquí aparece una diferencia fundamental.

Esto:

```java
Student
s.name
s.active
```

son entidades y atributos Java.

No estamos consultando directamente:

```text
student
name
active
```

Por eso estamos utilizando **JPQL**.

---

# Módulo 10. JPQL

JPQL consulta el modelo de entidades.

SQL:

```sql
SELECT *
FROM student
WHERE email = ?
```

JPQL:

```java
select s
from Student s
where s.email = :email
```

Diferencia:

```text
SQL  → tablas y columnas

JPQL → entidades y atributos
```

Ejemplo con relación:

```java
@Query("""
    select c
    from Course c
    where c.department.name = :department
""")
List<Course> findCoursesByDepartment(String department);
```

No escribimos manualmente:

```sql
JOIN department ...
```

Hibernate genera el SQL correspondiente.

---

# Módulo 11. JPQL con JOIN

Ejemplo:

```java
@Query("""
    select s
    from Student s
    join s.enrollments e
    join e.course c
    where c.id = :courseId
""")
List<Student> findStudentsEnrolledInCourse(Long courseId);
```

El estudiante debe aprender a leer mentalmente:

```text
Student
  ↓ enrollments
Enrollment
  ↓ course
Course
```

antes de escribir el JPQL.

---

# Módulo 12. Native SQL

También es posible:

```java
@Query(
    value = """
        SELECT s.*
        FROM student s
        WHERE s.email ILIKE CONCAT('%', :text, '%')
        """,
    nativeQuery = true
)
List<Student> searchByEmail(String text);
```

Spring Data JPA actual también proporciona `@NativeQuery` como alternativa especializada para consultas SQL nativas.

Pero debe enseñarse como una decisión consciente.

```text
JPQL
→ mayor independencia de la base

Native SQL
→ máximo control y características específicas
```

Por ejemplo PostgreSQL:

```text
ILIKE
JSONB
CTE
window functions
full text search
```

pueden justificar SQL nativo.

---

# Módulo 13. Regla para elegir el tipo de consulta

Utilizar esta jerarquía como criterio docente:

```text
¿La operación ya existe?
        │
       sí
        ▼
Método heredado
        │
       no
        ▼
¿La condición es sencilla y legible?
        │
       sí
        ▼
Query Method
        │
       no
        ▼
¿Puede expresarse claramente sobre entidades?
        │
       sí
        ▼
@Query + JPQL
        │
       no
        ▼
¿Necesita características PostgreSQL?
        │
       sí
        ▼
Native SQL
```

Ejemplos:

| Necesidad | Elección |
| --- | --- |
| Buscar ID | `findById` |
| Buscar email | Query Method |
| Buscar apellido ignorando mayúsculas | Query Method |
| Estudiantes matriculados en determinado departamento | JPQL |
| Reporte con múltiples JOIN y agregaciones | JPQL |
| Consulta JSONB PostgreSQL | Native SQL |
| Full-text search PostgreSQL | Native SQL |

# Práctica 2 — Flyway

No utilizaremos Hibernate para crear el esquema.

Configuración:

```yaml
spring:
  jpa:
    hibernate:
      ddl-auto: validate
```

La idea es:

```text
Flyway
   ↓
crea/modifica el esquema

Hibernate
   ↓
valida que las entidades coincidan
```

Spring Boot recomienda utilizar un único mecanismo responsable de la inicialización del esquema. Cuando se emplea Flyway no conviene mezclarlo con `schema.sql`, `data.sql` o generación automática de Hibernate.

# Práctica 3 — Primera migración

Crear:

```text
src/main/resources/
└── db
    └── migration
```

Contenido:

```sql
CREATE TABLE student (

    active BOOLEAN NOT NULL DEFAULT TRUE,
```

# Práctica 9 — Crear Enrollment

Introducir el siguiente requerimiento:

> CourseHub necesita conocer la fecha y el estado de cada matrícula.

Ahora:

```text
Student N:M Course
```

deja de ser suficiente.

Crear:

```text
Enrollment
-------------------
id
student_id
course_id
enrolled_at
status
final_grade
```

Migración:

```text
V3__create_enrollment.sql
```

La estructura Java será:

```java
@Entity
@Table(
    name = "enrollment",
    uniqueConstraints = @UniqueConstraint(
        name = "uk_enrollment_student_course",
        columnNames = {"student_id", "course_id"}
    )
)
public class Enrollment {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "student_id", nullable = false)
    private Student student;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "course_id", nullable = false)
    private Course course;

    @Column(nullable = false)
    private LocalDateTime enrolledAt;

    @Enumerated(EnumType.STRING)
    @Column(nullable = false)
    private EnrollmentStatus status;

    private BigDecimal finalGrade;
}
```

Esto permite introducir una idea fundamental:

> El modelo de persistencia debe representar reglas de negocio, no solamente relaciones entre objetos.

# Reglas de negocio

El proyecto debe implementar al menos:

```text
RB01
El email del estudiante debe ser único.

RB02
El código del curso debe ser único.

RB03
Un estudiante no puede matricularse dos veces
en el mismo curso.

RB04
Un curso pertenece exactamente a un departamento.

RB05
Una matrícula pertenece exactamente a
un estudiante y a un curso.

RB06
Una nota final debe estar entre 0 y 5.

RB07
No se puede asignar nota a una matrícula CANCELLED.
```

Algunas reglas pertenecen a Java.

Otras deben reforzarse en PostgreSQL.

Por ejemplo:

```sql
UNIQUE(student_id, course_id)
```

debe garantizar RB03 incluso si existe un error en el código Java.

```java
boolean existsByCode(String code);
```

### Consulta 3

Buscar cursos por departamento.

Puede resolverse mediante Query Method inicialmente:

```java
List<Course> findByDepartmentName(String departmentName);
```

### Consulta 4

Buscar estudiantes matriculados en un curso.

JPQL:

```java
@Query("""
    select e.student
    from Enrollment e
    where e.course.id = :courseId
      and e.status = :status
""")
List<Student> findStudents(
    Long courseId,
    EnrollmentStatus status
);
```

### Consulta 5

Contar matrículas activas.

```java
long countByStatus(EnrollmentStatus status);
```

### Consulta 6

Obtener promedio de notas de un curso.

```java
@Query("""
    select avg(e.finalGrade)
    from Enrollment e
    where e.course.id = :courseId
      and e.finalGrade is not null
""")
Double calculateAverageGrade(Long courseId);
```

# Integración con Testcontainers

Ahora abandonamos definitivamente la idea de probar persistencia únicamente contra bases en memoria.

La razón es simple:

```text
Producción → PostgreSQL

Pruebas → PostgreSQL
```

Testcontainers ejecuta bases de datos reales dentro de contenedores efímeros y evita depender de una instalación local o de diferencias de comportamiento entre H2 y PostgreSQL.

---

# Configuración con Spring Boot 4

Utilizaremos:

```java
@Testcontainers
@SpringBootTest
class StudentRepositoryIT {

    @Container
    @ServiceConnection
    static PostgreSQLContainer postgres =
            new PostgreSQLContainer("postgres:18.6-alpine");

}
```

Con Testcontainers 2.x el paquete recomendado es:

```java
import org.testcontainers.postgresql.PostgreSQLContainer;
```

en lugar del antiguo:

```java
org.testcontainers.containers.PostgreSQLContainer
```

que quedó deprecado.

`@ServiceConnection` permite que Spring Boot obtenga automáticamente URL, usuario, contraseña y demás detalles del contenedor sin tener que implementar manualmente un `@DynamicPropertySource`.

# Primera prueba de integración

```java
@Testcontainers
@SpringBootTest
class StudentRepositoryIT {

    @ServiceConnection
    static PostgreSQLContainer postgres =

    @Test

        assertThat(result.get().getEmail())

    }
}
```

```text
  ↓

  ↓

  ↓
PostgreSQL 18
  ↓

  ↓
Hibernate
  ↓
Repository
  ↓
Test
```

# Test de constraint real

No debemos probar solamente Java.

También debemos comprobar PostgreSQL.

```java
@Test
void shouldRejectDuplicatedEmail() {

    studentRepository.saveAndFlush(
        new Student(
            "Ana",
            "ana@coursehub.edu",
            LocalDate.of(2003, 1, 1)
        )
    );

    assertThatThrownBy(() ->
        studentRepository.saveAndFlush(
            new Student(
                "Otra Ana",
                "ana@coursehub.edu",
                LocalDate.of(2001, 2, 2)
            )
        )
    ).isInstanceOf(DataIntegrityViolationException.class);
}
```

El uso de:

```java
saveAndFlush()
```

es deliberado.

Queremos obligar a Hibernate a ejecutar el SQL durante el test para que PostgreSQL valide inmediatamente la restricción.

# @DataJpaTest vs @SpringBootTest

### `@DataJpaTest`

Útil para probar específicamente:

```text
Entities
Repositories
JPA
```

Spring Boot configura un slice enfocado en persistencia y, por defecto, ejecuta cada prueba en una transacción que se revierte al finalizar.

### `@SpringBootTest`

Carga:

```text
ApplicationContext completo
```

Lo utilizaremos en el proyecto cuando queramos comprobar de manera conjunta:

```text
Flyway
PostgreSQL
Hibernate
Repositories
Services
```

No significa que todos los tests deban usar `@SpringBootTest`.

La regla será:

```text
Repository aislado
      ↓
@DataJpaTest

Integración aplicación + DB
      ↓
@SpringBootTest
```

# ETAPA 4 — DOMINIO DE HABILIDADES CLAVE

En esta etapa dejamos de preguntar:

> ¿Cómo escribo una consulta?

y empezamos a preguntar:

> ¿Es una buena consulta?

---

# Habilidad 1 — Detectar N+1

Supongamos:

```java
List<Enrollment> enrollments =
    enrollmentRepository.findAll();

for (Enrollment enrollment : enrollments) {
    System.out.println(
        enrollment.getStudent().getName()
    );
}
```

Podríamos obtener:

```text
SELECT enrollment...

SELECT student WHERE id = 1
SELECT student WHERE id = 2
SELECT student WHERE id = 3
SELECT student WHERE id = 4
...
```

Esto es:

```text
1 consulta inicial
+
N consultas adicionales
```

Problema N+1.

Aprender a inspeccionar el SQL generado y no asumir que “si el código Java se ve corto, la consulta es eficiente”.

---

# Habilidad 2 — JOIN FETCH

Cuando sabemos que necesitamos una asociación:

```java
@Query("""
    select e
    from Enrollment e
    join fetch e.student
    where e.course.id = :courseId
""")
List<Enrollment> findByCourseWithStudent(Long courseId);
```

Conceptualmente:

```text
Lazy por defecto

+

Fetch explícito cuando el caso de uso lo necesita
```

es una estrategia más controlable que marcar indiscriminadamente relaciones como EAGER.

---

# Habilidad 3 — Entidades no son DTOs

Error frecuente:

```text
Controller
   ↓
Entity
   ↓
JSON
```

Las entidades representan persistencia.

No deberían utilizarse automáticamente como contrato HTTP.

Esto evita:

```text
LazyInitializationException
ciclos JSON
exposición accidental de datos
acoplamiento API ↔ persistencia
```

---

# Habilidad 4 — No utilizar CascadeType.ALL indiscriminadamente

Este código:

```java
@ManyToOne(cascade = CascadeType.ALL)
private Department department;
```

puede ser peligroso.

Eliminar un curso no debería necesariamente eliminar:

```text
Department
```

Las cascadas deben expresar:

```text
ciclo de vida compartido
```

y no simplemente comodidad.

---

# Habilidad 5 — equals() y hashCode()

No generar automáticamente:

```java
equals
hashCode
toString
```

utilizando todas las relaciones.

Puede provocar:

```text
carga inesperada de relaciones
recursividad
StackOverflowError
problemas con proxies Hibernate
```

Especialmente debe evitarse utilizar `@Data` de Lombok indiscriminadamente en entidades JPA.

---

# Habilidad 6 — Constraints en la base de datos

No confiar solamente en:

```java
if (!repository.existsByEmail(email)) {
    repository.save(student);
}
```

porque dos requests concurrentes podrían pasar simultáneamente la validación.

Debemos tener además:

```sql
UNIQUE(email)
```

La aplicación proporciona buena experiencia.

La base proporciona integridad.

---

# Habilidad 8 — Flyway como historial del sistema

El estudiante debe comprender que:

```text
V1
V2
V3
V4
```

representan la evolución de la base.

Por ejemplo:

```text
V1__create_student.sql

V2__create_department_course.sql

V3__create_enrollment.sql

V4__add_enrollment_status_index.sql

V5__add_student_profile.sql
```

No borrar y recrear `V1`.

Flyway compara las migraciones disponibles con las previamente aplicadas y mantiene el historial del esquema para que la evolución sea reproducible entre ambientes.

---

# Habilidad 9 — Índices

Consulta frecuente:

```sql
SELECT *
FROM enrollment
WHERE student_id = ?
AND status = ?
```

Podemos evaluar:

```sql
CREATE INDEX idx_enrollment_student_status
ON enrollment(student_id, status);
```

Aquí debe aparecer un nuevo nivel de razonamiento:

```text
JPA
no elimina
la necesidad de comprender SQL.
```

# 6. Errores que los estudiantes deben aprender a identificar

| Error | Problema |
| --- | --- |
| Utilizar `ddl-auto=update` como estrategia de producción | Esquema sin versionamiento controlado |
| Probar PostgreSQL únicamente con H2 | Diferencias de comportamiento |
| Hacer todas las relaciones EAGER | Sobrecarga y N+1 |
| `CascadeType.ALL` en todo | Eliminaciones inesperadas |
| Usar siempre `@ManyToMany` | Oculta entidades asociativas |
| Query Methods gigantes | Baja mantenibilidad |
| SQL nativo para consultas triviales | Acoplamiento innecesario |
| Usar entidades directamente como DTO | Acoplamiento API/persistencia |
| No definir constraints | Integridad dependiente de Java |
| Modificar migraciones ya desplegadas | Historial inconsistente |
| No probar constraints reales | Tests incompletos |
| Ignorar el SQL generado | Problemas de rendimiento invisibles |
| Usar `findAll()` sin pensar en volumen | Riesgo de memoria/rendimiento |

# 7. Regla de oro de consultas

El estudiante debería terminar el curso pensando así:

```text
1. ¿Spring Data ya proporciona la operación?
   → método heredado.

2. ¿La consulta puede expresarse claramente
   con 1-3 condiciones?
   → Query Method.

3. ¿La consulta necesita joins,
   agregaciones o mayor expresividad?
   → @Query + JPQL.

4. ¿Necesito funcionalidad específica
   de PostgreSQL o control SQL absoluto?
   → Native SQL.

5. ¿Estoy devolviendo más información
   de la necesaria?
   → revisar proyección/fetch.

6. ¿Qué SQL está ejecutándose realmente?
   → inspeccionar siempre que haya dudas.
```
